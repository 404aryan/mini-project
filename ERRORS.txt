[BUG-01] defaultPose.js calls ref.animate() — a method that does not exist on
  SignRuntimeLike.
  FILE: components/avatar/animations/defaultPose.js  (lines 13-16)
  CODE: if(ref.pending === false){ ref.pending = true; ref.animate(); }
  IMPACT: When defaultPose() is called outside AvatarPlayer (e.g. from signQueue's
    REST_POSE initialiser or from tests), it calls ref.animate() on a plain object
    that has no such method, causing a TypeError at runtime.  The same guard also
    tries to set ref.pending = true and call ref.animate(), but the signQueue runtime
    never has an .animate() method — only AvatarPlayer's internal loop drives
    playback.  REST_POSE is computed at module import time (top-level IIFE), so this
    crash can happen before any component even mounts.
  NOTE: Every individual Words/*.js and States.js animation file has the same
    identical finish() helper that does the same ref.animate() call. All of those
    are equally broken in any non-browser / test context, but because AvatarPlayer
    calls appendSignFrames() which splices the frames back out before finish() runs,
    the bug is silently swallowed in the browser.

[BUG-02] Live-backlog trimming in enqueueTokens() removes the wrong segment index.
  FILE: components/avatar/AvatarPlayer.tsx  (lines 567-571)
  CODE:
    while (runtime.segments.length > MAX_LIVE_BACKLOG) {
      runtime.animations.splice(runtime.segments[0].frames, runtime.segments[1].frames)
      runtime.segments.splice(1, 1)
    }
  PROBLEMS:
    a) runtime.animations.splice(start, deleteCount) treats segments[0].frames as a
       START INDEX, but segments[0].frames is a FRAME COUNT, not an index. The
       actual start index for segment[1] is segments[0].frames (accumulated), but
       because the same value is used as index AND count simultaneously, a random
       number of frames from the wrong position in the queue are deleted every time
       the backlog overflows. This corrupts the animation queue whenever live speech
       produces more than MAX_LIVE_BACKLOG (8) signs.
    b) segments.splice(1, 1) always drops the SECOND segment (index 1), not the
       oldest waiting one (index 0). The intent (from the comment) is to keep "the
       sign in progress and the newest speech; drop the oldest waiting signs", but
       dropping index 1 skips the sign currently playing. The correct approach would
       be to drop the OLDEST non-playing segment, which is index 1 only if index 0 is
       currently playing — but the code never checks whether segment 0 is already
       partially consumed by advanceFrame().

[BUG-06] advanceFrame() mutates the SignFrame array it is iterating by calling
  frame.splice(index, 1) inside the loop.
  FILE: components/avatar/signQueue.ts  (lines 78-94)
  CONTEXT: Mutating an array while iterating it with explicit index management is
    correct here only when splice() is called and index is NOT incremented. The
    current code does this correctly for deletion, but if a bone's delta lookup
    returns undefined (the bone is missing from this rig) it also splices without

[BUG-10] The avatar motion.div layout animation causes a visible jump when
  transitioning between normal layout and the sign-mode PiP.
  FILE: app/page.tsx  (line 666)
  CODE:
    <motion.div layout={!reducedMotion} layoutDependency={sign.active}
      className={`avatar-stage ... ${sign.active ? 'sign-avatar-pip' : ''}`}
      transition={{ type: 'spring', stiffness: 170, damping: 25 }}>
  When sign.active becomes true, React immediately applies the sign-avatar-pip class
  (position:fixed, 170×210 px) BEFORE Motion can measure the old layout. The layout
  measurement sees the element already in its new CSS position, so the spring starts
